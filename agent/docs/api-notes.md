# API 노트: 설계 가정과 실제 동작의 차이

설계(`design.md`)는 실행해 보지 않은 스케치입니다. 설치된 버전(`requirements.lock`)에서 다르게 동작한 것을 한 줄씩 적습니다.
형식: `가정 → 실제 → 대응` (확인한 파일·테스트)

## M0 뼈대

- `.gitignore`는 3.2절 6개 항목(.venv/ __pycache__/ .pytest_cache/ var/ .langgraph_api/ .env)이면 충분 → setuptools 편집 설치(`pip install -e`)가 `src/glople_agent.egg-info/`를 만듦 → `*.egg-info/`를 더함
- `LANGGRAPH_STRICT_MSGPACK=true`는 실행 환경변수로 켜면 됨 → checkpoint 4.2.0은 `langgraph.checkpoint.serde._msgpack` import 때 한 번만 읽고(`_msgpack.py:12`), langgraph 1.2.12는 `compile()` 때 state·context 스키마로 허용 목록을 만듦(`graph/state.py:1234`) → `tests/conftest.py` 맨 위에서 langgraph import 전에 설정. CLI·서비스 진입점도 import 전에 설정해야 함
- `BearerToken.__reduce__`의 TypeError는 pickle만 막음 → `copy.copy`·`copy.deepcopy`도 `__reduce_ex__`를 거쳐 같은 TypeError → 그래프는 `context=`를 복사하지 않아 문제없음(`test_context.py::test_context_reaches_node_without_leaking`). 우리 코드에서 context·config를 deepcopy하지 않음

## M0 일정 확인(plan)

- `langgraph.errors.is_invalid_resume(e)`로 스키마 위반 재개를 판별(9.1·E3, 1.2.16 소스) → 1.2.12에는 이 함수가 없음. `interrupt(response_schema=)`는 재개 값을 `TypeAdapter(...).validate_python`으로 검사해 `pydantic.ValidationError`를 invoke 밖으로 그대로 올리고, 검사가 `scratchpad.resume.append` 앞이라 아무것도 저장되지 않아 같은 interrupt에 다시 답할 수 있음(`types.py:1009-1017`) → 호출부는 그래프를 부르기 전에 `PlanDecision.model_validate(값)`으로 먼저 검사해 422로 돌려주고(노드 안의 다른 ValidationError와 섞이지 않게), invoke에서 올라온 `ValidationError`도 같은 422로 처리 (`tests/test_plan.py::test_plan_decision_with_real_interrupt`)
- `Command(resume=PlanDecision(...))`처럼 모델 객체로 재개해도 됨 → 재개 원값이 체크포인트 `__resume__` 쓰기에 그대로 저장되고, STRICT에서 다시 읽을 때 `Blocked deserialization of glople_agent.plan.draft.PlanDecision` 경고와 함께 dict로 풀림(동작은 함) → 재개 값은 dict로 넘김: `PlanDecision.as_resume()` (scratchpad 실험, checkpoint 4.2.0)

## M0 동작 고정(`tests/test_pins_langgraph.py`, 부록 A)

langgraph 1.2.12·prebuilt 1.1.0·checkpoint 4.2.0·langchain-core 1.6.6에서 확인함. 설계와 같았던 것은 테스트로만 고정했고 여기에는 다른 점과 확인하지 못한 점만 적음.

- `is_invalid_resume`(A4) → 위 '일정 확인' 절과 같음: 1.2.12에는 없고 `pydantic.ValidationError`가 그대로 올라오며, 같은 id의 interrupt가 남고 체크포인트 수도 그대로라 다시 답할 수 있음. 다만 실패한 재개에서도 노드가 처음부터 다시 돌아 interrupt 앞 코드는 실행됨 → interrupt 앞에는 부작용을 두지 않음. 버전을 올리면 `hasattr` 고정 테스트가 깨지니 그때 공식 함수로 바꿈 (`test_invalid_resume_raises_validation_error_and_can_answer_again`)
- `nostream` 태그·`disable_streaming` 모델은 messages 스트림에 안 나옴(A11, 12절) → 토큰 조각은 안 나오지만, 노드가 state에 돌려준 메시지는 노드가 끝날 때 통째로 한 번 나옴(`AIMessage`, Chunk 아님, `pregel/_messages.py` on_chain_end). 그래서 route의 tool_calls AIMessage도 messages 모드에 나옴 → 토큰 출력은 `meta["langgraph_node"] == "answer_llm"`이면서 `isinstance(chunk, AIMessageChunk)`인 것만 씀 (`test_messages_mode_streams_chunks_and_node_outputs`)
- `after_route`는 `remaining_steps ≤ 3`이면 fallback(5.4) → recursion_limit 25에서 첫 노드가 24를 보고 단계마다 1씩 줄어듦. remaining_steps가 0인 노드도 실행은 되지만 다음이 END여도 그 뒤에 GraphRecursionError가 남. 그래서 노드 n개짜리 경로는 recursion_limit ≥ n+1이어야 하고, 지금 노드 뒤에 k개가 더 돌려면 remaining_steps ≥ k+1이어야 함. 3이면 fallback→finish는 끝나지만(2, 1), 4에서 재시도하면 route(3)→validate(2)→tools(1)→collect(0) 뒤에 오류가 남 → 재시도 조건은 "remaining_steps ≥ 재시도한 route 뒤 가장 긴 경로의 노드 수 + 2"로 둠(M0 템플릿 경로 validate·tools·collect·answer_template·finish 5개면 7 이상, M2에 answer_llm이 붙으면 8 이상). 그보다 작으면 fallback (`test_last_node_needs_one_remaining_step`, `test_retry_guard_with_remaining_steps_reaches_end`)
- 재개 때 recursion_limit 예산을 이어 쓴다고 가정할 수 있음 → invoke마다 새 예산임. 재개 실행에서 다시 도는 interrupt 노드는 recursion_limit+1(25면 26)부터 셈 → edit 3회도 한도를 나눠 쓰지 않음. 단계 수 상한은 턴(invoke) 단위로만 생각함 (`test_resume_gets_fresh_step_budget`)
- 같은 재개를 두 번 보내면 저장이 두 번 될 수 있다고 봄(9.2 1번) → 대기 interrupt가 없는 스레드에 `Command(resume=...)`를 보내면 아무 노드도 돌지 않음(no-op). 하지만 값만 보낸 재개는 지금 대기 중인 interrupt에 그대로 들어감: edit 뒤 새 카드(새 id)가 떠 있으면 예전 화면의 승인이 새 카드에 적용됨. `Command(resume={interrupt_id: 값})`로 보내면 id가 다를 때 적용되지 않고 같은 카드가 다시 뜸 → 호출부는 대기 id 검사(9.2)를 유지하면서 재개를 `{interrupt_id: 값}` 꼴로 보냄. `resume()`의 `interrupt_id`는 필수(아래 'M0 리뷰 반영') (`test_resume_without_pending_interrupt_is_noop`, `test_resume_by_interrupt_id_ignores_stale_id`)
- 같은 노드가 다시 interrupt를 내면 id도 같을 수 있음 → edit 뒤 review를 다시 지나면 새 id(체크포인트 ns·task id로 만든 해시)이고, `get_state().interrupts`에는 새 것 하나만 남음 → 9.2의 "id가 다르면 거절"이 그대로 성립 (`test_get_state_interrupts_holds_only_pending`)
- 재개할 때 context는 따로 챙기지 않아도 됨 → context는 저장되지 않아서 `context=` 없이 재개하면 `runtime.context`가 None임. 새 context로 재개하면 다시 도는 노드부터 새 값을 봄 → CLI·서비스는 재개 invoke마다 그때의 `AgentContext`를 넘기고, `save_plan`은 `bearer is None`을 로그인 필요로 처리 (`test_resume_needs_context_again`)
- `interrupt(response_schema=Pydantic)`·`StructuredTool(args_schema=Pydantic)`이 타입을 엄격히 검사함 → 둘 다 느슨한 모드라 `"3"` → `3`으로 바꿔 통과시킴 → 문자열 숫자를 막으려면 validate 노드(라우터 인자)나 `check_edit`(재개 값)에서 따로 검사하고, 필요하면 모델에 `strict=True`를 둠 (`test_toolnode_coerces_args_with_pydantic_schema`, `test_interrupt_response_schema_returns_validated_model`)
- `handle_tool_errors=tool_error_to_json`는 도구 실행 예외만 받음(8.1) → 인자 검증 실패(`ToolInvocationError`)도 같은 함수로 옴. 또 함수 첫 인자의 타입 주석으로 잡을 예외가 정해져서 `e: TimeoutError`처럼 좁게 쓰면 나머지는 다시 던짐 → `def tool_error_to_json(e: Exception) -> str`로 두고, 안에서 `ToolInvocationError`는 `bad_request`로 나눔. 오류 ToolMessage의 `artifact`는 None이라 collect가 카드를 따로 만들어야 함 (`test_toolnode_callable_error_handler_returns_tool_message`, `test_toolnode_handler_annotation_limits_caught_types`)
- `content_and_artifact` 도구는 (content, artifact)를 돌려줌 → 튜플이 아니면 ValueError가 나고, 기본 오류 처리는 이것을 다시 던져 그래프가 멈춤 → 레지스트리 함수는 항상 `make_result`의 튜플을 돌려줌 (`test_content_and_artifact_tool_must_return_tuple`)
- ToolNode를 단독으로 `invoke`해 단위 시험할 수 있음 → 그래프 밖에서 부르면 `ValueError: Missing required config key 'N/A' for 'tools'`(Runtime 주입 필요) → 한 노드짜리 StateGraph에 얹어 시험함 (`test_toolnode_needs_graph_runtime`)
- `add_node(destinations=)`는 갈 수 있는 곳을 제한함(5.4) → 그림(draw_mermaid 점선)에만 쓰이고 실행 때는 막지 않음. 목록 밖 goto도 실행되고, 없는 노드 이름 goto(오타)는 예외 없이 무시되어 그래프가 그냥 끝남(경고 로그 `wrote to unknown channel branch:to:<이름>`). 정적 엣지가 있는 노드가 `Command(goto=)`를 내면 엣지를 대체하지 않고 둘 다 실행됨 → goto 대상은 상수로 두고 경로 테스트로 지키며, Command를 내는 노드(plan_prepare·review·save_plan)에는 정적 엣지를 달지 않음 (`test_goto_outside_destinations_still_runs`, `test_goto_unknown_node_is_ignored_with_warning`, `test_command_goto_adds_to_static_edges`)
- `RemoveMessage`로 지울 메시지가 없어도 됨 → 없는 id를 지우면 `ValueError: Attempting to delete a message with an ID that doesn't exist` → validate는 이번 턴 라우터 AIMessage id가 messages에 있을 때만 RemoveMessage를 냄 (`test_remove_message_with_unknown_id_raises`)
- 확인 못 함: SqliteSaver 파일·`metadata` 열에 context가 없는지(A2의 Sqlite 쪽) → M0에는 langgraph-checkpoint-sqlite를 깔지 않음(3.3, M3부터) → M3에서 `test_token_hygiene`에 sqlite 판을 더함
- 확인 못 함: ChatOpenAI·HTTP 쪽 가정(A7~A10, A12: `bind_tools` JSON, `logit_bias` 키, artifact 직렬화, `finish_reason`·`invalid_tool_calls`, openai 3.24.0과의 왕복) → 가짜 OpenAI 서버가 필요하고 8090 접속 금지라 M1 범위 → M1의 HTTP 동작 고정 테스트로 넘김
- 확인 못 함: `add_node(timeout=)`(async 노드 전용이라는 조사 결과), `error_handler=`, 서브그래프 interrupt 전파·`get_state(subgraphs=True)`, `stream_events(version="v3")` → M0 그래프가 쓰지 않음(timeout·error_handler는 미사용, 서브그래프는 M3) → 쓰기 시작하는 단계에서 이 파일에 고정 테스트를 더함

## M0 그래프 조립(`graph/`, `cli.py`, `eval/replay.py`)

langgraph 1.2.12·prebuilt 1.1.0·checkpoint 4.2.0에서 확인함. 설계 5·9·10절과 다르게 둔 것만 적음.

- route에 `RetryPolicy(max_attempts=2, retry_on=연결 오류)`를 걸고 연결 오류는 `route → fallback`(5.4)으로 보냄 → 노드가 예외를 잡으면 RetryPolicy가 못 보고, 다시 던지면 두 번째 실패에서 예외가 그래프 밖으로 나가 fallback에 닿지 않음. 1.2.12의 `runtime.execution_info.node_attempt`(1부터, 재시도마다 +1, `pregel/_retry.py:597-610`)로 지금이 마지막 시도인지 알 수 있음 → route는 `node_attempt < 2`일 때만 연결 오류를 다시 던지고(RetryPolicy가 같은 단계에서 한 번 더), 마지막 시도에서는 잡아서 `router_kind="error"` → fallback("모델에 연결하지 못했어요"). RetryPolicy 재시도는 같은 단계라 remaining_steps를 쓰지 않음 (`test_pins_langgraph.py::test_runtime_execution_info_counts_retry_attempts`, `test_graph_paths.py::test_connection_error_twice_goes_fallback`)
- `after_route`는 `remaining_steps ≤ 3`이면 fallback(5.4·작업 지시) → 위 '동작 고정' 절대로 3으로는 재시도 경로가 END까지 못 감 → `edges.py`에 경로 길이로 정함: 재시도는 `remaining_steps ≥ 7`(템플릿 모드, llm 모드 8), 도구 경로는 `≥ 6`(llm 7), 모자라면 fallback("단계가 너무 길어졌어요"). 도구 경로를 못 타고 fallback으로 가면 route가 넣은 호출은 finish가 cancelled ToolMessage로 닫음. recursion_limit 25에서는 route가 23을 봐서 실제로 걸리지 않고, 테스트는 recursion_limit 6·8로 확인 (`test_low_remaining_steps_skip_retry_and_go_fallback`, `test_low_remaining_steps_for_tool_path_closes_router_call`)
- 확인 카드가 떠 있는 스레드에 새 메시지를 보내는 경우는 M3에서 다룸(9.3) → 1.2.12는 대기 interrupt가 있어도 새 입력(Command 아님)이면 START부터 다시 돌고 예전 interrupt는 버림. 그러면 create_travel_plan tool_call이 짝 없이 남음 → `start_turn`이 지난 턴의 짝 없는 호출을 cancelled ToolMessage로 닫음(새 HumanMessage 뒤에 붙어 순서는 `[AI(호출), Human, Tool]`이지만 라우터는 이전 대화를 받지 않고, M2 답변 프롬프트도 이번 턴만 씀). 호출부(CLI)는 9.3대로 먼저 `cancel_pending`(reject 재개)으로 닫음 (`test_new_input_while_interrupt_pending_drops_it`, `test_hitl.py::test_new_message_while_card_pending`)
- `interrupt()`에서 멈춘 노드도 `updates` 스트림에 노드 이름이 나옴 → 멈춘 노드는 updates 조각이 없고 `__interrupt__` 조각만 옴(review가 path에 안 보임) → `TurnResult.path`는 실제로 끝난 노드만 담고, 대기 카드는 스트림이 끝난 뒤 `get_state().interrupts`로 읽음(12절). CLI는 path 뒤에 `review(확인 대기)`를 덧붙여 보여 줌 (`test_hitl.py::test_interrupt_returns_confirm_card`)
- `langgraph.errors.is_invalid_resume(e)`로 판별(9.1) → 1.2.12에 없음(위 절). interrupt의 검증 오류는 `TypeAdapter(PlanDecision)`이 내므로 `ValidationError.title == "PlanDecision"` → `graph.is_invalid_resume(e)`를 둠: 우리 `InvalidResume`(호출부 `resume()`이 그래프를 부르기 전에 `PlanDecision.model_validate`로 검사해 냄, 422) 또는 title이 PlanDecision인 ValidationError면 True. 노드 안의 다른 ValidationError와 섞이지 않음 (`test_schema_violation_resume_is_invalid_and_card_stays`, `test_is_invalid_resume_only_for_plan_decision_errors`)
- `update_state`·노드 반환으로 BearerToken을 state에 넣으면 저장에서 오류(A6) → 둘 다 `TypeError: Type is not msgpack serializable: BearerToken`이고 저장소에 평문이 남지 않음. A6은 설계 그대로 성립 (`test_token_hygiene.py::test_bearer_token_in_state_update_fails`, `test_bearer_token_returned_by_node_fails`)
- validate는 통과한 호출을 그대로 남김(5.3) → 인자를 실행 모델로 한 번 정규화해 넣음(`validate_args(...).model_dump(exclude_none=True)`: `"28"`→28, MBTI 대문자, 앞뒤 공백 제거). ToolNode도 느슨하게 바꿔 주지만(위 절), create_travel_plan은 ToolNode를 거치지 않고 `make_draft`가 정수만 받기 때문. 정답 390건은 정규화 뒤에도 정답 호출과 이름·인자까지 같음 (`test_numeric_string_args_are_normalized_before_tools`, `test_replay.py::test_replay_matches_oracle_answers_exactly`)
- 일정과 다른 호출이 섞이면 나머지에 "한 번에 하나씩 처리할게요" ToolMessage(error)를 붙여 짝을 닫음(5.4) → validate가 라우터 메시지를 통과한 호출만으로 교체하므로 빠진 호출은 messages에 없어 닫을 짝이 없음 → verdict에 `plan_not_alone`을 남기고 finish가 최종 답 앞에 그 문장을 붙임 (`test_plan_mixed_with_other_call_keeps_plan_only`)

## M0 리뷰 반영

그래프 조립 뒤 리뷰에서 나온 문제를 재현해 고친 것. langgraph 1.2.12·checkpoint 4.2.0에서 확인함.

- 9.2 1겹 "대기 id가 다르면 거절" → `resume()`의 `interrupt_id`가 선택 인자라 빼면 그 순간 대기 중인 id로 채워져 값만 보낸 재개와 같았음. edit·401·check_draft 뒤 새 카드가 떠 있으면 같은 요청이 두 번 올 때 두 번째가 사용자가 못 본 새 카드에 들어감(edit 두 번 적용, 401 카드 자동 승인) → `interrupt_id`를 필수 키워드 인자로 바꿈. 호출부는 화면에 띄운 `TurnResult.pending.id`를 보관해 넘기고(CLI `ChatSession.shown_card`, `eval/replay.py`, 테스트 `GraphKit.last`), 지금 대기 중인 id로 닫는 곳은 `cancel_pending`(reject)뿐. M5 AI7 본문의 `interruptId`도 필수 (`test_hitl.py::test_resume_requires_interrupt_id`, `test_double_submit_after_401_does_not_approve_new_card`, `test_double_submit_of_edit_applies_once`)
- 9.2 2겹 "저장 노드는 같은 client_request_id의 결과가 state에 있으면 건너뜀" → 그래프 안에서 닿을 수 없음. `start_turn`이 results를 턴마다 비우고, 저장에 성공하면 경로는 finish → END뿐이며, END 뒤 `invoke(None)`·대기 interrupt 없는 재개는 아무 노드도 돌리지 않음. save_plan이 다시 도는 길은 저장 전 체크포인트에서 다시 실행(시간 여행)이나 저장 직후 중단뿐인데, 그때 state에는 저장 기록이 없어 state 검사로는 막지 못함(고의로 검사를 꺼도 그래프 테스트가 하나도 깨지지 않았음) → 2겹을 지우고(`already_saved` 삭제) 1겹(대기 id)과 3겹(저장소 멱등키)만 둠. 시간 여행에서도 멱등키로 1건 (`test_hitl.py::test_save_plan_reruns_only_by_time_travel_and_store_key_dedupes`, `test_same_resume_twice_saves_once`)
- GraphRecursionError면 정해진 사과 문장(5.4) → 1.2.12는 finish가 remaining_steps 0에서 END에 닿아도 그 뒤에 오류를 내서, 체크포인트에는 finish의 진짜 답이 저장됐는데 화면에는 사과 문장이 나갔음(recursion_limit 4 직답) → `_stream`이 오류를 잡은 뒤 `snapshot.next == ()`이고 이번 실행의 마지막 노드가 finish면 성공으로 봄(error None, 저장된 final_text). END 전에 멈춘 경우만 사과 문장이고, 이때 대화 기록에는 답이 없음(다음 턴 start_turn이 짝 없는 호출을 닫음) (`test_graph_paths.py::test_recursion_error_after_end_keeps_stored_answer`, `test_recursion_error_is_caught_by_caller`)
- 11절 ⑥ "원문은 cards에만, messages에는 안 들어감" → `content_and_artifact` 도구의 ToolMessage.artifact에 원문 카드가 통째로 실려 messages 채널에 남음. messages는 상한이 없어 MAX_CARDS=60도 소용없음(70턴 뒤 artifact 쪽 sentinel 210개) → collect가 카드를 만든 뒤 같은 id의 ToolMessage로 교체해 artifact를 `{"card_id"}` 참조로 줄임(add_messages가 제자리에서 바꿈, content는 그대로). 단 tools 노드 직후의 지난 체크포인트(`get_state_history`)에는 원문 artifact가 남음. 설계가 말한 '체크포인트 복제 저장'과 같은 범위로 보고, M3 Sqlite·M5 정리 때 다시 봄 (`test_token_hygiene.py::test_type3_text_stays_in_cards_not_messages`)
- `start_turn`이 짝 없는 tool_call을 cancelled ToolMessage로 채움(12절) → ToolMessage만 닫으면 확인 카드가 `plan_confirm`·`ok`로 남아, reject 재개(`error`, `data.cancelled=True`)와 결과가 달랐음(M5 화면 복원에 죽은 카드가 살아 보임) → 닫는 호출이 create_travel_plan이면 같은 card_id 카드를 `error`·`cancelled`로 교체하고 card 이벤트도 냄(turn_id는 그 카드가 뜬 턴 그대로) (`test_hitl.py::test_new_message_while_card_pending`)
- 확인 카드 edit의 `PlanDraftIn.places`는 모양만 검사(9.1) → `apply_edit`는 목록의 장소를 모두 사용자가 고른 것(USER_EDIT, selected)으로 봐서, 화면이 해제된 MODEL_SUGGESTED까지 기본값으로 다시 보내면 지어낸 장소가 저장됨(CLI `e`에서 장소 칸을 비운 경우) → places는 '저장할(선택한) 장소 목록'이라는 계약을 Field description(interrupt의 response_schema에 실림)과 주석에 적고, CLI 기본값을 선택된 장소만으로 바꿈(해제된 제안은 안내만). M5 PlanConfirmCard도 같은 계약 (`test_cli.py::test_chat_edit_with_blank_places_keeps_unselected_suggestion_out`)
- `clean_text`는 '지운 자리에서 다시 생기는 조합'이 없어질 때까지 반복하고 500자 자르기는 끝에서(5.3) → 일부러 겹친 입력(`<<<b>b>b>`)은 한 바퀴에 한 겹씩 벗겨져 O(n²)(72KB 한 마디가 약 8초, start_turn·check_edit에서) → 반복은 `MAX_PASSES`(8)번까지, 그래도 안정되지 않으면 꺾쇠를 모두 지움(특수 토큰·태그는 모두 `<`로 시작). max_len이 있으면 정제 전에 `max(max_len×8, 1024)`자로 먼저 자르고, 일정 칸 정제는 필드 한도의 4배를 max_len으로 줌. 72KB 7ms, 900KB(제한 없음) 86ms. 무작위 조합 20만 개 + 깊은 겹침 fuzz에서 Qwen 특수 토큰 26개 중 남은 것 0. M5 요청 본문 크기 상한은 따로 둠 (`test_sanitize.py::test_nested_input_cost_is_linear`, `test_deeper_than_max_passes_still_clean`)
